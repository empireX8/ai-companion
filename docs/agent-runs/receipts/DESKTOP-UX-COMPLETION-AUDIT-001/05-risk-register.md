# Risk Register

## Highest risks if repair order is wrong

1. Fixing visual polish before inspector trust
- Risk: the app looks better while still presenting evidence badly.
- Outcome: false confidence and another failed live validation.

2. Fixing Today routing before decision-state honesty
- Risk: users reach the right page, but the page still records fake or misleading state.
- Outcome: flow feels less broken, but trust is still broken.

3. Reopening Model Goals / Mind Context / selection foundations
- Risk: queue expands into architecture churn instead of completion work.
- Outcome: safe repair slices become another parity cycle.

4. Expanding capture into generic chat improvements
- Risk: product drifts toward journaling/chat instead of evidence-backed understanding.
- Outcome: product truth violation.

5. Repairing Watch For visually before contract clarification
- Risk: styling hides unclear semantics.
- Outcome: fieldwork still feels random even if the page looks cleaner.

## What can be deferred

Can defer until after the core blockers:
- voice input coverage
- import repair
- Explore grounding polish
- Timeline continuity polish
- brand polish

## What must not be deferred

Must not defer if desktop launch-readiness is the goal:
- Inspector trust repair
- Decisions state honesty
- Today re-entry route correctness
- Capture contract repair
